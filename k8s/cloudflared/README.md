# cloudflared (Cloudflare Tunnel)

The shared **public front door** for the cluster. One locally-managed Cloudflare
Tunnel exposes selected in-cluster services to the internet — no inbound ports,
home IP hidden, real TLS. Routing lives in this repo (the ConfigMap), not in the
Cloudflare dashboard.

This folder is **service-agnostic infrastructure**: the connector, its
credentials, and the central routing table. Anything specific to a service it
fronts (hostnames it hardens, its client setup) lives in that service's own
folder.

**Currently exposed:** Immich — see [`../immich/README.md`](../immich/README.md).

The `ingress:` list in the ConfigMap is your single source of truth for *what is
reachable from the internet*. Keep it that way.

## Files

| File | Committed | Purpose |
|---|---|---|
| `00-namespace.yml` | yes | `cloudflared` namespace |
| `01-sealed-secret.yml` | yes | generated by `./seal.sh` from `secret.yml` (tunnel credentials) |
| `02-configmap.yml.tmpl` | yes | template for the tunnel config (the ingress routing table) |
| `02-configmap.yml` | **no** | generated by `./gen-config.sh` from `config.env`; keeps hostnames out of git |
| `03-deployment.yml` | yes | the `cloudflared` connector deployment |
| `access-token.sh` | yes | manage Cloudflare Access service tokens (API/mobile clients) |
| `secret.yml` / `config.env` / `cloudflare.env` | **no** | your local, uncommitted values |
| `*.example` | yes | copy these to create the local files |

Secrets kept out of git: the tunnel credentials (sealed into
`01-sealed-secret.yml`), the public hostnames (rendered into the ignored
`02-configmap.yml`), and the Cloudflare API token (`cloudflare.env`).

## One-time setup

### 1. Domain onto Cloudflare
Add your domain as a site in Cloudflare and switch your registrar's nameservers
to the ones Cloudflare gives you. Wait until the zone is **Active**.

### 2. Create the tunnel (Cloudflare dashboard, no CLI)
1. **Zero Trust -> Networks -> Tunnels -> Create a tunnel -> Cloudflared.**
   Name it (e.g. `homelab`) and save.
2. **Skip the "Public Hostnames" step** — routing is handled locally by the
   ConfigMap. Leaving it empty avoids a remote/local config conflict.
3. On the install screen, copy the **token** (the long string after `--token`).
   Do not install anything.
4. Decode it:
   ```bash
   echo "<TOKEN>" | base64 -d
   # -> {"a":"<AccountTag>","s":"<TunnelSecret>","t":"<TunnelID>"}
   ```

### 3. DNS record (Cloudflare dashboard)
In **DNS -> Records**, add a **CNAME** for each hostname you expose:
- **Name**: the subdomain (e.g. `app`)
- **Target**: `<TunnelID>.cfargotunnel.com`
- **Proxy**: Proxied (orange cloud)

The `<TunnelID>` must be the plain UUID (the token's `t` field). This CNAME is
what makes the hostname resolve to your tunnel.

### 4. Fill in the two local files
```bash
cd k8s/cloudflared

cp secret.yml.example secret.yml
# edit secret.yml: remap a->AccountTag, s->TunnelSecret, t->TunnelID

cp config.env.example config.env
# edit config.env: DOMAIN=app.example.com, TUNNEL_ID=<t>
```

### 5. Deploy
From the repo root:
```bash
make cloudflared
```
This checks that `secret.yml` and `config.env` exist (and tells you how to
create them if not), runs `./seal.sh` and `./gen-config.sh`, `kubectl apply -k`,
then `rollout restart` (a ConfigMap/Secret change alone does not restart a
running pod, so the restart is what makes edits take effect). Verify:
```bash
kubectl -n cloudflared logs deploy/cloudflared -f   # expect "Registered tunnel connection"
```

> Re-run `make cloudflared` any time you change `config.env` or `secret.yml`.

## Protect it: Cloudflare Access (the CVE shield)
A tunnel exposes the service's whole surface (login, API) to the internet. Put
**Cloudflare Access** in front so anonymous traffic is stopped at Cloudflare's
edge, before it reaches the origin — this is what lets you expose an app without
babysitting every CVE.

In **Zero Trust -> Access -> Applications**, add a self-hosted app per hostname:
- **Allow** policy, selector **Emails** = the people allowed in, auth method
  **One-time PIN** (6-digit email code; no account needed).
- Optional per app: **Bypass** policies for specific public paths.

### API / mobile clients (service tokens)
Access uses an interactive browser login, so native apps and API clients (which
talk straight to the API) get bounced by the OTP page. Give them a
non-interactive credential — a **service token** — instead. This keeps the
shield: requests still need a valid token.

1. **Zero Trust -> Access -> Service Auth -> Service Tokens -> Create.** Copy the
   Client ID and Client Secret (secret shown once).
2. On the app's Access application, add a second policy with action
   **`Service Auth`** (NOT "Allow", which would still force the login), Include
   -> Service Token. Keep the One-time PIN policy for browsers; both coexist.
3. The client sends two headers:
   - `CF-Access-Client-Id` = `<Client ID>`
   - `CF-Access-Client-Secret` = `<Client Secret>`

Do NOT "fix" a blocked app by bypassing `/api/*` in Access — that exposes the
app's whole API unauthenticated.

### One-click token management (`access-token.sh`)
Instead of clicking the dashboard per person/device, use the helper.

**One-time policy setup:** on the Access application, make the Service Auth
policy Include = **"Any Access Service Token"**. Then adding/revoking a client is
just creating/deleting a token — no policy edits. (Trade-off: any service token
in your account is accepted by that app. Fine if tokens are only used here;
otherwise list specific tokens in the policy.)

**One-time config:** `cp cloudflare.env.example cloudflare.env` and fill in a
Cloudflare API token scoped to just `Account -> Access: Service Tokens -> Edit`,
plus your account ID.

```bash
cd k8s/cloudflared
./access-token.sh create alice    # prints the two headers ONCE -> enter on the client
./access-token.sh list            # see who has a token
./access-token.sh revoke alice    # instantly cut off that client, nobody else affected
```
Needs `jq`. One token per person/device = clean per-client revocation.

## Expose a new service
1. **Route:** in `02-configmap.yml.tmpl`, add an `ingress:` entry (before the
   `http_status:404` catch-all) with a `__DOMAIN_FOO__` hostname placeholder,
   pointing at the target `Service`
   (`http://<svc>.<namespace>.svc.cluster.local:<port>`).
2. **Config:** add the matching `DOMAIN_FOO=foo.example.com` to `config.env`.
   `gen-config.sh` substitutes any `__KEY__` from `config.env` automatically, so
   the new hostname stays out of git — no script changes needed.
3. **DNS:** add a proxied CNAME `<host> -> <TunnelID>.cfargotunnel.com`.
4. **Access:** add an Access application for the new hostname (+ service token
   policy if it has API/mobile clients).
5. `make cloudflared`
6. Document the service-specific bits (hostname, client setup, hardening) in
   *that service's* folder, not here.

> Note: `01-sealed-secret.yml` and `02-configmap.yml` do not exist until you run
> `./seal.sh` and `./gen-config.sh`, so `kubectl apply -k` will fail before that —
> by design, so nothing sensitive is committed.
